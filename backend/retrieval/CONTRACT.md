# Retrieval ↔ Answer interface agreement (Person 2)

Status: agreed by Person 2; **Person 3 must confirm the validator + `/api/ask/`
orchestration match this.** This is the document the task "agree how evidence
passages and source IDs are passed to the answer logic" refers to.

Spec refs: `devpost/spec.md` §Retrieval, §Generation, §Response Validation;
`docs/requirements.md` §7.2, §9.

## Pipeline

```
question ─► retrieve() ─► [evidence passages] ─► generate_answer() ─► validate ─► client
              │  layer 1: insufficient_evidence, no model call
              └  layer 2: model may itself abstain
```

## 1. Evidence passage shape (retrieval → generation → validator)

An **evidence passage** is a plain dict. Required key:

| key | type | meaning |
|---|---|---|
| `text` | str | the passage body that gets quoted and grounded on |
| `source_id` | str | the citation id used in `cited_source_ids` |

Recommended keys, passed through untouched when present (they become the
source cards):

| key | type | source |
|---|---|---|
| `passage_id` | str/int | Passage row id (Person 3's model) |
| `document_id` | str/int | Document row id |
| `title` | str | document title |
| `url` | str | public URL or `/api/documents/<id>/file/` |
| `section` | str | section heading |
| `page` | int | page number (omit when none) |
| `date` | str | publication/effective date, `YYYY-MM-DD` |
| `status` | str | `current` / `superseded` / `unknown` |
| `score` | float | relevance, added by `retrieve()` (0..1) |

**Rule:** retrieval returns these dicts *as-is plus `score`*. It never drops
metadata, so a citation can always be rendered without a second lookup.

## 2. `retrieve(question, ...) -> list[dict]`

`retrieval/search.py`:

- `retrieve()` — ranked evidence passages, each with `score`.
- `retrieve_with_status()` — `(status, passages)` where status is
  `retrieved` or `insufficient_evidence`.

**Layer 1 (abstain, no model call):** no hits, OR query-term coverage below
`MIN_COVERAGE`, OR best score below `MIN_SCORE`. Current calibrated values:
`MIN_SCORE=0.3`, `MIN_COVERAGE=0.33` (see `evaluate_thresholds`).

## 3. `generate_answer(evidence, question) -> dict`

`retrieval/generation.py`. **Exact output contract:**

```json
{ "status": "answered | insufficient_evidence | conflicting_sources | error",
  "answer": "string or null",
  "cited_source_ids": ["..."],
  "message": "string or null" }
```

**Hard invariant:** every id in `cited_source_ids` MUST be a `source_id`
present in the `evidence` list that was passed in. Unknown ids are dropped;
if that removes all support the result becomes `insufficient_evidence`.

This is the same status vocabulary as the API contract
(`devpost/spec.md`, `docs/requirements.md` §9). Note `conflicting_sources`
and `error` — Person 3's `api/serializers.py` currently omits
`conflicting_sources` and must add it.

## 4. Who owns which check

| check | owner | location |
|---|---|---|
| ranking, layer-1 abstain, coverage/MIN_SCORE | Person 2 | `retrieval/search.py` |
| grounding prompt, layer-2 abstain, citation filtering | Person 2 | `retrieval/generation.py` |
| final structural validation before the client | Person 3 | `api/validators.py` |
| retrieval + generation unit tests | Person 2 | `retrieval/tests/` |
| end-to-end `/api/ask/` orchestration | Person 3 | `api/views.py` |

Person 3's validator may re-implement the rules from §3 but must return the
same shape; `conflicting_sources` requires ≥2 distinct `document_id`s.

## 5. Fallback `contact_line`

Layer-1 `insufficient_evidence` responses carry `contact_line`
(office name + its source) supplied by Person 1's corpus metadata. It is
attached by the API layer from the corpus config — **never** generated by
the model. Retrieval itself does not produce it.

## 6. Testability without a key (FR-04)

Retrieval is fully testable offline. Generation is tested offline with an
injected fake provider (`set_provider()`), and live tests are skipped unless
`AI_API_KEY` is set.
